## 1. Область применения и контекст проекта

Проект представляет собой клиентскую библиотеку SDK для платформы MAX Bot API (`pkg/maxbot`, `pkg/bot`, `pkg/fsm`) и автономный сервис искусственного интеллекта (`cmd/ai-bot`).

С точки зрения работы с базами данных:
1. Проект следует принципу **Zero External Dependencies** для ядра SDK, поэтому здесь осознанно **не используются** тяжелые сторонние ORM (GORM, Ent) или генераторы кода (sqlc).
2. Единственный модуль взаимодействия с БД в SDK — это `pkg/fsm/sql.go`, предоставляющий реализацию постоянного хранилища конечных автоматов (`fsm.Storage`) поверх стандартного интерфейса Go `database/sql.DB`.

## 2. Результаты проверки

### 2.1 Контекст и отмена запросов (`context.Context`)
- **Статус:** ✅ **Соответствует**
- Все операции с базой данных в [pkg/fsm/sql.go](file:///C:/mimocode/max-bot-api-client/pkg/fsm/sql.go) строго используют методы с контекстом:

  - `ExecContext(ctx, ...)`
- Вектор утечек соединений при отмене клиентского запроса или таймауте контекста отсутствует.

### 2.2 Параметризация запросов и защита от SQL Injection
- **Статус:** ✅ **Соответствует**
- Все пользовательские параметры (`user_id`, `chat_id`, `state`, `data`, `updated_at`) передаются строго через позиционные параметры подстановки (`?`), предотвращая любые типы SQL-инъекций.
- Имя таблицы подставляется через `fmt.Sprintf`:
  - По умолчанию имя таблицы захардкожено как `"fsm_states"`.
  - При кастомной передаче через `SQLStorageOptions{TableName: ...}` рекомендуется валидировать имя таблицы на алфавитно-цифровые символы и подчеркивания во избежание некорректных SQL-идентификаторов.

### 2.3 Транзакционность и конкурентный доступ (Race Conditions)
- **Статус:** ⚠️ **Рекомендация по улучшению**
- В [pkg/fsm/sql.go](file:///C:/mimocode/max-bot-api-client/pkg/fsm/sql.go) в методах `SetState`, `SetData` и `UpdateData` используется паттерн проверки наличия записи:
  ```go
  err := s.db.QueryRowContext(ctx, checkQuery, key.UserID, key.ChatID).Scan(&dummy)
  if err == sql.ErrNoRows {
      // INSERT
  } else {
      // UPDATE
  }
  ```
- Для одного процесса это защищено `s.mu.Lock()`. Однако при горизонтальном масштабировании бота (несколько реплик в Dokploy/Kubernetes, работающих с общей SQLite/Postgres БД) между `SELECT` и `INSERT` возможна гонка `UNIQUE constraint failed`.
- **Рекомендация:** Использовать диалект-агностический или нативный `UPSERT` (`INSERT ... ON CONFLICT (user_id, chat_id) DO UPDATE ...` для SQLite 3.24+ / PostgreSQL, либо `INSERT ... ON DUPLICATE KEY UPDATE` для MySQL), либо оборачивать связку в явную транзакцию `tx, err := s.db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})`.

### 2.4 Диалектные плейсхолдеры SQL
- **Статус:** ⚠️ **Замечание**
- Текущие SQL-запросы в `pkg/fsm/sql.go` используют плейсхолдер `?` (стандарт SQLite и MySQL).
- При подключении PostgreSQL драйвер `lib/pq` или `pgx/stdlib` ожидает плейсхолдеры вида `$1, $2, $3`.
- **Рекомендация:** Добавить в `SQLStorageOptions` опцию `Dialect` (`DialectSQLite`, `DialectPostgres`, `DialectMySQL`), автоматически адаптирующую плейсхолдеры при формировании запросов.

### 2.5 Управление ресурсами и соединениями
- **Статус:** ✅ **Соответствует**
- `Close()` корректно делегирует закрытие пула соединений в `s.db.Close()`.
- Ресурсы `QueryRow` освобождаются автоматически при вызове `Scan`.

## 3. Итог

Модуль `pkg/fsm/sql.go` обеспечивает надежное базовое хранение FSM поверх стандартного `database/sql` без привнесения внешних зависимостей. Для многонодовых сред рекомендуется внедрить поддержку атомарного UPSERT и диалекта PostgreSQL.
